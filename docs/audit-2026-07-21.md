# Auditoría técnica inicial - 21 de julio de 2026

## Stack detectado

- Frontend y backend web: React 19 con TanStack Start y TanStack Router.
- Runtime: Nitro con preset `cloudflare-module`; despliegue mediante Wrangler a Cloudflare Workers con Assets.
- Lenguaje: TypeScript 5.8 en modo estricto, objetivo ES2022.
- Construcción: Vite 8 y configuración de `@lovable.dev/vite-tanstack-config`.
- Estilos: Tailwind CSS 4, variables CSS y componentes compatibles con shadcn/ui (Radix UI).
- Iconos: Lucide React.
- Datos remotos: Supabase JS 2.108, PostgreSQL, Storage privado y Row Level Security.
- Estado servidor: TanStack Query 5.
- Formularios/validación: React Hook Form, resolvers y Zod están instalados; buena parte de las pantallas existentes usa estado local.
- Autenticación: correo y contraseña de Supabase Auth. El perfil asociado define los roles `Administrador` y `Personal`.
- Navegación: rutas basadas en archivos de TanStack Router.
- IA existente: chatbot Lex mediante una función de servidor y Groq. La clave se lee del entorno del servidor.
- Integración externa existente: Google Calendar OAuth desde el navegador y sincronización con la agenda del CRM.

## Módulos y rutas existentes

- Dashboard: `/`.
- Clientes: `/clientes` y `/clientes/$id`.
- Casos: `/casos` y `/casos/$id`. Esta entidad ya representa funcionalmente un expediente.
- Documentos: `/documentos`, Supabase Storage y asociaciones opcionales con cliente/caso.
- Agenda: `/agenda`, con asociaciones opcionales y sincronización con Google Calendar.
- Pagos: `/pagos`, visible para administradores.
- Reportes: `/reportes`, visible para administradores y personal.
- Configuración: `/configuracion`, visible para administradores.
- Búsqueda global: clientes, casos, documentos, reportes, agenda y pagos según rol.

## Tablas actuales

`profiles`, `clients`, `cases`, `payments`, `payment_records`, `agenda_events`, `documents` y `client_reports`.

Los CRUD principales están implementados con hooks de TanStack Query. No existe todavía una capa de repositorios o servicios de dominio; parte de la lógica de negocio está dentro de las rutas.

## Estado de seguridad

- RLS está habilitado en las tablas actuales.
- Las funciones `is_staff()` e `is_admin()` comprueban rol y estado activo.
- Lectura y escritura operativa están limitadas a personal activo; eliminación sensible se reserva principalmente al administrador.
- El bucket `documents` es privado y entrega enlaces temporales.
- No se detectó una `service_role` en el frontend. La anon key incluida en el cliente no concede privilegios por sí sola y depende de RLS, aunque conviene mantener toda configuración en variables de entorno.
- El sistema es de una sola organización. No existe `organization_id`; por ello no se afirma aislamiento multiempresa en esta fase.

## Problemas y riesgos detectados

1. No hay pruebas automatizadas ni script `test`.
2. `database.types.ts` se mantiene manualmente y puede desincronizarse del esquema real.
3. Varias rutas superan 500 líneas y mezclan consultas, reglas de negocio, formularios y presentación.
4. `schema.sql` conserva políticas iniciales permisivas y luego las sustituye por políticas finales. El resultado final es correcto al ejecutar el archivo completo, pero la lectura y mantenimiento son propensos a errores.
5. Las migraciones previas dependen del orden de creación de `is_staff()`/`is_admin()`; ya hubo un fallo por esa dependencia.
6. `cases` y `documents` tienen un modelo reducido para reconstrucción procesal: no existen partes, actuaciones, fuentes, tareas ni estados de análisis.
7. Pagos no tiene relación directa con expediente; solo con cliente.
8. La búsqueda es estructurada, limitada y una consulta nueva fallida puede invalidar el conjunto si se usa `Promise.all`.
9. Los formularios actuales no normalizan de forma uniforme DNI, teléfono ni códigos de expediente.
10. No hay borrado lógico ni bitácora general de cambios. Esta fase añadirá trazabilidad de origen y fechas, pero no reemplazará los borrados existentes.

## Decisiones de migración

- Mantener `cases` como tabla canónica de expedientes y conservar la ruta `/casos` para no romper enlaces. La interfaz utilizará el término “Expedientes”.
- Mantener las columnas heredadas de `clients`, `cases` y `documents`. Las columnas nuevas serán opcionales o tendrán valores compatibles derivados de las existentes.
- Añadir tablas para partes, actuaciones, tareas, extracciones, importaciones, ejecuciones de análisis, hallazgos y referencias de fuente.
- Crear las funciones de rol al inicio de la nueva migración para evitar dependencias de orden.
- No insertar datos demostrativos en las tablas reales. Los módulos preliminares usarán proveedores simulados claramente etiquetados.
- No conectar Google Drive, OCR ni modelos de análisis documental reales en esta fase.
- Mantener los permisos actuales: administradores y personal activos acceden a la información jurídica; las eliminaciones sensibles quedan para administradores.
- Preparar contratos para Cloudflare Queues/Workflows sin configurar recursos reales.

## Compatibilidad prevista

Las consultas existentes usan `select('*')` o columnas heredadas, por lo que las ampliaciones no invalidan registros previos. Los nuevos campos se rellenan con valores derivados cuando existe una equivalencia segura, por ejemplo `document_number = dni`, `case_number = expediente`, `case_type = process_type` y `court = juzgado`. No se elimina ni renombra ninguna columna.
