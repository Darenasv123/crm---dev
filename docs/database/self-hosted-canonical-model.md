# Modelo canónico de Supabase self-hosted

Fecha de diseño: 2026-08-07. Objetivo: Supabase self-hosted sobre PostgreSQL 17.6, base vacía. Este documento describe el resultado de ejecutar, en orden, `supabase/self-hosted/0001` a `0007`; `0008_verify.sql` solo lee y verifica.

## Decisiones de alcance

El modelo final contiene 25 tablas `public`. Se incorporan las seis funcionalidades locales consultadas: `document_folders` y las cinco tablas `google_calendar_*`. Todas están referenciadas por el CRM actual y no son código muerto. No se incluye ninguna vista, enum PostgreSQL, event trigger global, objeto de `cleanup_backup_20260804`, dato operativo, backfill o columna creada solo para eliminarse después.

No se requiere una extensión externa. En PostgreSQL 17, `gen_random_uuid()` es nativa. El bootstrap sí exige que la instalación Supabase ya tenga `auth.users`, `storage.buckets` y `storage.objects`.

## Constraints e índices

Conteo esperado de constraints: 125 = 25 PK + 59 FK + 39 CHECK + 2 UNIQUE. Los CHECK cubren roles/estado, estados del dominio, importes y cuotas, porcentajes/confianza, tamaños, tipos documentales, sincronización, ciclos triviales y estados de tareas. Los tipos documentales permitidos son exactamente `Demanda`, `Resolución`, `Sentencia`, `Poder`, `Contrato`, `Otros`; el test estático conserva esa lista como contrato canónico y la compara con el CHECK SQL. La integración frontend debe adoptar el mismo contrato cuando sus cambios se incorporen por separado.

## Funciones y RPC

Hay 21 funciones `public`:

- Autorización/Auth: `crm_is_active_staff`, `crm_is_active_admin`, wrappers `is_staff`, `is_admin`, y `handle_new_user`.
- Infraestructura/validación: `set_updated_at`, `check_folder_parent_same_client`, `check_folder_no_cycle`, `check_document_folder_same_client`, `validate_document_relationship`, `validate_case_task_relationship`.
- Auditoría/documentos: `audit_document_metadata`, `normalize_document_types(boolean)`.
- Tareas: `apply_case_task_completion`, `guard_case_task_schedule`, `guard_case_task_update`, `audit_case_task_changes`, `log_case_task_event`, `claim_case_task(uuid)`, `return_case_task(uuid)`.
- Pagos: `register_payment_record_atomic(uuid,numeric,text,text,text,date)`.

Las cuatro RPC invocables por `authenticated` son `claim_case_task`, `return_case_task`, `normalize_document_types` y `register_payment_record_atomic`; también se concede EXECUTE a los cuatro helpers de compatibilidad/autorización, para ocho grants de función en total.

## RLS, policies y grants

Las 25 tablas tienen RLS habilitada explícitamente. No existe `rls_auto_enable`, `ensure_rls` ni event trigger global.

Hay 78 policies `public`:

- `profiles`: `profiles_select`, `profiles_update_admin` (2).
- Trece tablas operativas (`clients`, `cases`, `document_folders`, `documents`, `client_reports`, `case_parties`, `document_extractions`, `case_events`, `import_jobs`, `import_folders`, `ai_analysis_runs`, `ai_findings`, `source_references`): policies `{tabla}_{select,insert,update,delete}` (52). Staff activo selecciona/inserta/actualiza; solo Admin activo elimina.
- `payments` y `payment_records`: cuatro policies cada una, todas solo Admin activo (8).
- `agenda_events`: lectura Staff; insert/update/delete Admin (4).
- `case_tasks`: lectura Staff; creación y borrado Admin; actualización Admin o Personal asignado, además del guard (4).
- Historias: `case_task_history_select`, `document_change_history_select` (2); solo lectura Staff, escrituras mediante triggers.
- Google: cuatro policies Admin en conexiones, una lectura Admin en canales y una lectura Admin en log (6). `google_calendar_oauth_states` y `google_calendar_sync_requests` tienen RLS sin policies para `authenticated`.

Storage añade 4 policies, para 82 totales: staff activo SELECT/INSERT/UPDATE de objetos del bucket `documents`; solo Admin activo DELETE.

Los grants se reinician explícitamente. `anon` y `PUBLIC` no reciben acceso; `authenticated` recibe solo los privilegios de tabla que las policies restringen y ocho EXECUTE concretos; `service_role` recibe acceso completo a tablas/secuencias y funciones. Las tablas internas OAuth/webhook no tienen grants para `authenticated`.

## Auth y seguridad

`handle_new_user` fija siempre `role='Personal'` y `status='Activo'`. Solo toma de metadata nombre y teléfono; nunca lee `raw_user_meta_data.role`, `status`, `is_active` ni permisos. En conflicto actualiza únicamente nombre, email, teléfono e iniciales. La FK `profiles.id → auth.users.id` se conserva con borrado en cascada.

La edición directa de perfiles se reserva a Admin activo. Es más restrictiva que permitir que cada usuario edite sus datos personales, pero coincide con la pantalla actual de administración y evita que un único UPDATE mezcle datos personales con campos de autorización. Si el producto añade un perfil personal editable, debe exponerse mediante una RPC con lista blanca de columnas, no relajando la policy actual.

Las funciones `SECURITY DEFINER` fijan `search_path=''`; EXECUTE se revoca a `PUBLIC`, `anon` y `authenticated` antes de conceder únicamente los puntos de entrada. Los triggers pueden invocar sus funciones sin grant de usuario. El informe ampliado está en `docs/database/self-hosted-security-review.md`.

## Storage

Bucket `documents`, privado, sin migrar objetos. `file_size_limit` y `allowed_mime_types` quedan en `NULL`: no se impone un límite arbitrario capaz de romper importaciones actuales. Los límites de proxy/servidor deben medirse antes de fijar una cuota. Las cuatro policies sustituyen las siete policies Cloud solapadas.

## Compatibilidad de extensiones y versión

El Cloud auditado tenía `plpgsql 1.0` en `pg_catalog`, `pgcrypto 1.3`, `uuid-ossp 1.1` y `pg_stat_statements 1.11` en `extensions`, y `supabase_vault 0.3.1` en `vault`. El bootstrap canónico requiere solamente capacidades núcleo de PostgreSQL 17 y los esquemas de plataforma Auth/Storage. No usa `uuid-ossp`, Vault ni estadísticas, y no instala extensiones. La disponibilidad/versionado exactos de extensiones opcionales del self-hosted no se ha supuesto ni consultado, porque esta fase prohíbe conectarse/aplicar SQL; si una integración futura las necesita, el preflight debe consultar `pg_available_extensions` y `pg_extension` en modo lectura. No se utiliza funcionalidad exclusiva de PostgreSQL 18.

## Diferencias intencionales

Frente al Cloud: se agregan `document_folders`, cinco tablas Google, los dos historiales y sus funciones actuales; se corrigen Auth/perfiles; se reduce Storage de siete a cuatro policies; se elimina el event trigger RLS; se usa un solo guard de tareas; `agenda_events.google_event_id` reemplaza el legado no usado `gcal_event_id`; no se copia `cleanup_backup_20260804`.

Frente a migraciones históricas: no se reproducen 23 ALTER/DROP/hotfix/backfill, funciones reemplazadas, policies supersedidas, comprobaciones de IDs concretos ni datos históricos. Las tablas nacen con su forma final y las funciones existen una sola vez.

## Procedimiento posterior de prueba

1. Preparar una instancia Supabase desechable, vacía y con PostgreSQL 17.x; confirmar Auth y Storage base.
2. Capturar en modo lectura `server_version`, `pg_available_extensions` y `pg_extension` para registrar diferencias del servidor real.
3. Ejecutar `0001` a `0007` en orden con un rol propietario autorizado, deteniéndose ante el primer error. No usar las migraciones históricas.
4. Ejecutar `0008_verify.sql`; no continuar si aparece cualquier fila `FAIL`.
5. En una transacción de prueba, crear identidades separadas para Personal activo, Admin activo e inactivo. Validar la matriz anon/Personal/Admin/inactivo/service_role, y hacer rollback o eliminar la instancia desechable.
6. Probar dos sesiones concurrentes reclamando la misma tarea: una debe ganar el lock y la otra debe recibir “ya no disponible”. Probar devolución, finalización e historiales.
7. Probar relación documento/tarea contra un expediente de otro cliente; ambas operaciones deben fallar.
8. Probar sobrepago concurrente y acceso Personal al RPC de pagos; deben fallar.
9. Subir/leer/actualizar/eliminar un objeto temporal del bucket según cada rol; confirmar bucket privado y luego limpiar la instancia desechable.
10. Regenerar tipos, sin edición manual: `npx supabase gen types typescript --db-url "postgresql://..." --schema public > src/lib/database.types.ts` desde una copia/entorno controlado, revisar el diff y ejecutar la suite completa antes de sustituir el archivo del producto.

Riesgos pendientes: disponibilidad operativa real de Auth/Storage en la imagen self-hosted; límites HTTP/Storage externos a PostgreSQL; cifrado y rotación de `encrypted_refresh_token`; configuración del webhook Google; semántica de privilegios del rol propietario; y drift que solo puede descartarse aplicando el bootstrap en una instancia desechable.
